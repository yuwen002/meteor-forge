# 租户定时健康巡检设计

> 状态：Schema v16、Store、调度器、Server 生命周期、配置/历史 API 与前端配置/历史页面已实现；持续补充生命周期、权限边界与前端请求竞态回归测试  
> 前置分支：`feat/tenant-connection-health-check`（PR #12）  
> 目标分支：`main`

## 1. 背景与现状

当前租户连接健康能力支持手动单租户/批量巡检，并在管理元数据库中保存每个租户的**最新一次**结果。最新结果表采用 `tenant_id` 唯一键覆盖写入，因此不能用于趋势分析或故障发生时间追溯。

本阶段在保留现有手动巡检 API 和最新状态查询兼容性的前提下，增加可控的后台定时巡检与独立历史记录。

## 2. 本阶段范围

### 包含

- 全局定时巡检配置：启用状态、巡检间隔、单次连接超时、历史保留天数。
- 后台调度器：启动时加载配置；配置变更后生效；关闭服务时停止并等待正在执行的任务。
- 仅巡检状态为 `active` 的租户；跳过 `suspended` 租户。
- 复用现有连接池、健康检查器和脱敏结果，不为每个租户创建独立连接池。
- 将每次巡检结果追加写入历史表，同时更新现有最新状态表。
- 提供配置读取/更新、历史分页查询 API。
- 前端增加定时巡检配置和历史记录入口。
- 历史数据按保留策略清理，并限制单次清理量，避免阻塞正常请求。

### 不包含

- 多实例分布式调度之外的通用任务编排；本次增加基于管理元数据库的租户巡检租约。
- 邮件、Webhook、短信等外部告警。
- 自动禁用租户、自动修复或自动切换数据源。
- 任意租户独立巡检计划、复杂 Cron 表达式。
- 对历史记录做不可逆的聚合压缩。

## 3. 配置与安全边界

建议默认关闭定时巡检，避免升级后未经用户明确启用就对目标数据库产生额外连接流量。

| 配置 | 默认值 | 约束 |
|---|---:|---|
| enabled | false | 布尔值 |
| interval_seconds | 300 | 30–86400 秒 |
| timeout_seconds | 5 | 1–30 秒 |
| history_retention_days | 30 | 1–365 天 |
| concurrency | 4 | 固定安全上限，最大 4 |

配置由管理元数据库持久化。更新配置必须校验完整边界；禁用时取消下一轮调度，正在执行的巡检应按服务关闭语义安全收尾；因请求取消或服务关闭而中断的检查不应写入 unhealthy 历史，也不应覆盖最近一次有效状态。不得将 DSN、密码、驱动原始错误写入历史记录或 API 响应。

## 4. 数据模型建议

### 4.1 巡检配置

新增单行配置表 `admin_tenant_health_settings`：

- `id`：固定主键（例如 1）。
- `enabled`、`interval_seconds`、`timeout_seconds`、`history_retention_days`。
- `updated_at`。

### 4.2 巡检历史

新增 `admin_tenant_connection_health_history`，每次执行追加一条：

- `id`：自增主键。
- `tenant_id`：租户 ID。
- `source`：`manual` 或 `scheduled`。
- `status`：`healthy` 或 `unhealthy`。
- `checked_at`、`duration_ms`、`message`：仅保存标准化信息。

索引建议：`(tenant_id, checked_at DESC, id DESC)` 与 `(checked_at DESC, id DESC)`。租户删除后的历史数据处理策略需与现有外键/审计保留约定一致；优先保留租户 ID 快照，不因租户删除而级联清空运维证据。

现有 `admin_tenant_connection_health` 继续作为每个租户最新状态的快速读取表，避免破坏当前列表 API 和前端。历史写入与最新状态更新应在同一管理库事务中完成。

## 5. 调度器行为

1. 调度器由管理 API Server 持有，生命周期与 Server 一致。
2. 服务启动后读取配置；仅在 enabled=true 时启动下一轮计时。
3. 每轮开始时读取当前 active 租户列表，按固定并发上限执行巡检。
4. 单租户失败不影响其他租户；结果顺序与租户列表无关，历史记录按实际完成时间写入。
5. 调度循环同步执行每一轮巡检和清理；上一轮完成前不会启动下一轮，因此不会发生轮次重叠。下一轮间隔从上一轮清理完成后重新计时。
6. 配置更新通过通知通道重置计时器，不依赖轮询配置表；配置读取失败时记录错误，并在 30 秒后重试，也可由配置更新通知提前触发重载。
7. 关闭服务时停止计时器、取消调度上下文，并等待当前巡检/清理退出；调度器的 Start/Close 均幂等，关闭前未启动的实例也可安全关闭，关闭后不能重新启动。
8. 配置读取、巡检执行和历史清理错误均通过服务日志上报。
9. 每轮巡检前通过管理元数据库中的单行租约记录竞争执行权；租约包含 owner、到期时间和递增 generation。持有者每 10 秒续约一次，租约默认 30 秒；续约失败或所有权丢失时取消当前轮次。每条定时巡检结果在写入事务内再次校验 owner、generation 和租约有效期，防止过期实例在新持有者接管后继续写入。进程异常退出后，其他实例可在租约到期后接管。租约使用 SQLite 条件 UPDATE 原子竞争，不依赖进程内锁。未取得租约的实例跳过本轮，不执行巡检和历史清理。
10. 多实例必须共享同一个管理元数据库文件，并处于 SQLite 支持的共享文件系统/锁语义范围内；当前建议仅在同一主机的本地文件系统上运行多个 API 进程。不得将独立 SQLite 副本当作共享协调存储，也不要依赖不保证文件锁语义的网络文件系统。多实例主机应保持系统时钟同步。

## 6. API 草案

路径均相对于 `/api/v1`。

### 配置

- `GET /tenant-health/settings`：返回当前配置。
- `PUT /tenant-health/settings`：更新完整配置并立即生效。

### 历史

- `GET /tenant-health/history`：分页查询历史。
- 支持 `tenant_id`、`status`、`source`、`from`、`to`、`limit`、`cursor`。
- 默认按 `checked_at DESC, id DESC` 稳定排序；限制最大页大小（建议 100）。
- 时间参数采用 RFC3339；拒绝非法时间范围和未知状态/来源。
- 返回结构包含 `items`、`next_cursor`，不返回数据库连接配置。

### 现有接口兼容

- `GET /tenant-health` 仍返回最新状态，不默认改成历史列表。
- 手动巡检 API 保持原路径与响应结构，但其结果同时写入历史，`source=manual`。
- 定时巡检写入 `source=scheduled`。

## 7. 前端交互

- 租户健康页增加“定时巡检”开关、间隔、超时、保留天数配置。
- 显示最近一次巡检时间和状态；区分手动与定时来源。
- 历史列表支持租户、状态、来源、时间范围筛选和游标分页；筛选变化会重新从第一页加载，过期请求不能覆盖较新的筛选结果。
- 时间范围按 RFC3339（UTC ISO 8601）传给 API；切换筛选条件后从第一页重新查询。
- 窄屏下筛选控件允许换行，避免挤压历史表格。
- 历史筛选请求使用递增序号保护，只允许最新请求更新列表、游标、错误提示和加载状态；加载更多在已有请求或游标为空时不重复提交。
- 禁用状态明确显示“定时巡检未启用”，不将“没有历史记录”误显示为健康。
- 保存配置失败时保留用户输入并展示后端校验错误；保存成功后刷新当前配置。

## 8. 测试与验收标准

### Store / migration

- 配置默认值、边界值、非法值和并发更新。
- 历史追加写入；最新状态与历史记录原子一致。
- 分页排序稳定；筛选组合正确；空结果与超大页大小处理。
- 保留策略只删除过期记录，不误删新记录或其他租户记录。

### Scheduler

- 默认关闭；启用后按间隔执行；配置变更立即生效。
- 上一轮未完成时不会重叠启动。
- 单租户失败不阻塞其他租户。
- 服务关闭后不再启动任务，且等待中的任务可取消。
- 并发数不超过 4；单次连接检查遵守 timeout。
- suspended 租户不参与定时巡检。
- 使用短间隔和超时保护调度器测试；测试必须覆盖关闭、取消、配置读取失败恢复和错误上报。
- 在长间隔待执行期间关闭配置并刷新，确认不会再启动巡检轮次。

### API / UI / CI

- 前端请求序号与分页准入逻辑有独立单元测试，并在 Web Admin CI 中执行。
- RBAC 权限矩阵覆盖配置读写和历史查询。
- 输入校验、未授权访问、数据库异常均有回归测试。
- API 文档、部署说明、用户手册同步更新。
- Web Admin、Go 测试、Lint、数据库驱动集成 CI 全部通过。

## 多实例调度状态排查

通过 `GET /api/v1/tenant-health/scheduler` 查看本实例的进程内执行统计和共享租约状态：

- `held_by_this_instance`：本实例当前持有有效租约，且租约代次可用于 fencing。
- `held_by_other_instance`：另一实例持有有效租约，本实例会跳过本轮。
- `expired_or_unclaimed`：当前没有有效持有者，等待下一轮竞争；若长期持续出现，应检查巡检配置、调度日志和元数据库访问。
- `unavailable`：本次无法读取租约状态，接口仍返回进程内统计；检查管理元数据库连接和日志。
- `not_configured`：本实例未能配置租约身份，不能执行安全的多实例调度。

`lease_expires_at` 和 `lease_remaining_seconds` 仅在有效租约存在时提供；`lease_generation` 在每次新持有者接管时递增。接口不会暴露随机 owner ID、DSN 或数据库驱动错误。该状态是当前查询时刻的观测值，不是全局历史统计。


## 多实例故障恢复验收

- **异常退出接管**：实例异常退出时不会主动释放租约；其他实例只能在租约到期后原子接管，generation 必须递增。旧实例即使恢复，也不能续约、释放新实例的租约，或通过旧 generation 写入巡检结果。
- **元数据库不可用**：持有租约的实例在续约失败或无法确认租约所有权时，必须取消当前巡检上下文并停止后续工作；租约丢失后跳过本轮历史清理。数据库恢复后由新持有者按租约到期规则接管。
- **恢复边界**：接管不代表可以并行执行旧实例中尚未结束的外部连接检查。巡检实现必须遵守 context 取消；对结果写入仍以数据库中的 owner 与 generation fencing 校验为最终保护。
- **部署建议**：所有实例必须访问同一份管理元数据库；独立 SQLite 副本不能提供跨实例协调能力。多实例共享 SQLite 文件时应部署在同一主机的本地文件系统，并保持主机时钟同步。


## 多实例并发与重复执行验收补充

- 使用多个独立 Store 连接同一管理元数据库同时竞争时，只有一个执行器可以进入巡检回调；其余实例必须跳过本轮。
- 持有者失去租约后，即使旧执行器尚未完全退出，新持有者的 generation 也会阻止旧执行器写入；旧执行器延迟执行的释放操作不得清除新持有者的租约。
- 租约丢失的轮次不执行历史清理。只有仍持有有效租约、且未检测到租约丢失的执行器才进入清理阶段。
- 这些保护用于避免重复写入和重复清理；外部连接检查仍须响应 context 取消。对无法取消的底层驱动调用，不能仅依靠租约保证其物理操作立即停止。

## 租约运行统计

`GET /api/v1/tenant-health/scheduler` 在进程内快照中提供以下多实例协调计数：

- `lease_skipped_count`：因其他实例持有有效租约而跳过的轮次数。此类竞争结果不计入 `total_runs`。
- `lease_lost_count`：巡检执行期间续约失败或确认失去租约的次数。对应轮次会取消，并跳过后续历史清理。
- `lease_acquire_failure_count`：获取租约时发生元数据库访问错误的次数，与正常竞争失败分开统计。

这些计数仅在当前 API 进程内维护，重启后归零，不代表多实例全局累计值。排查多实例问题时，应结合每个实例的状态快照、服务日志和共享租约到期时间判断；不要将不同实例的计数直接当作唯一任务总数。
